## What you can build

A research article usually stops at the page: it states a result, and the reader takes it on
trust. Latent Writing Lab lets you publish one the reader can operate. You write prose in
Markdown, math in LaTeX and sources in BibTeX, and you add figures that respond to the reader:
sliders, drawings, filters, step-by-step animations. One build turns the same sources into a
themed website, a PDF and stand-alone figure pages that any other site can embed.

Draw a digit in the figure below. The network classifies it as you draw, and every layer
updates with your stroke.

The articles are built by Thibaud Frere's
[research-article-template](https://github.com/tfrere/research-article-template), the engine
behind Hugging Face's long-form research posts such as the
[Smol Training Playbook](https://huggingface.co/spaces/HuggingFaceTB/smol-training-playbook).
The engine supplies the layout, math, citations, theming, table of contents and exports. Latent
Writing Lab adds what a project needs around it: figure pages other sites can embed, browser
tests that operate your figures, CI, and this documentation, which runs on the same engine. Every
example on these pages is live.

## Quick start

You need Git and Node.js 22.12 or later. Clone the repository, install, and start the preview:

```sh
git clone https://github.com/cris96spa/latent-writing-lab.git
cd latent-writing-lab
npm ci
npm run dev
```

The preview runs at [http://127.0.0.1:4321/](http://127.0.0.1:4321/) and shows the
template's demonstration article, which uses every component the engine offers. Saving a file
refreshes the page. To read these docs locally next to it, run `make doc` in a second terminal
and open [http://127.0.0.1:8031/](http://127.0.0.1:8031/).

<Accordion title="Start your own article project">

On GitHub, choose **Use this template → Create a new repository** on the starter's page, then
clone your new repository instead. The template copies the starter's files into a project with
a history of its own; fork the starter only to contribute back to it. One repository holds one
article: a new section is another chapter, and a draft is a branch.

On Windows, work inside WSL, which keeps the repository's symbolic links intact. On every
start, Astro prints two `[WARN] [content]` lines about `article.mdx` and `figures.json`; the
template produces them, and the article builds normally.

</Accordion>

Your article is defined by one file, `app/src/content/article.mdx`, which starts out importing
the template's demonstration. Clear it out in one step:

```sh
make demo-remove
```

The command deletes the demonstration's chapters, figures and data, keeps everything these docs
use, and writes a one-chapter article with a browser test. It leaves the change uncommitted, so
`git status` shows exactly what went. The article it writes is these two files, which you can
also create by hand. `article.mdx` names the title and the chapters:

```mdx
---
title: "My first article"
template: "paper"
authors: []
showPdf: false
---

import Intro from "./chapters/intro.mdx";

<Intro />
```

`app/src/content/chapters/intro.mdx` holds the chapter:

```mdx
import HtmlEmbed from "../../components/HtmlEmbed.astro";

## A first section

Inline math such as $e^{i\pi} + 1 = 0$, and a display equation:

$$
\int_0^1 x^2 \, dx = \frac{1}{3}
$$

```

Either way, the preview shows your title, the equations and a live function plotter. The

## How the pieces fit

Three rules explain almost everything the engine does:

1. **What you import is what you publish.** `article.mdx` imports the chapters, in reading
   order. A chapter it imports is published, and a chapter it does not import is not. There is
   no draft flag.
2. **Each figure has one source.** A figure is one HTML file. The article, the figure's own page
   and any site that embeds it all render that file, so one fix reaches every reader.
3. **Readers get the build, not your preview.** Readers receive the static site the build
   writes, or a PDF in which each figure is a still image of the state it opens in. Checks and
   exports therefore run on the build.
