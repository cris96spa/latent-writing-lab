## Let readers test the claim

Hand them the mechanism as a figure they can operate. The routing figure below takes a
sentence that readers would otherwise have to believe, "a mixture-of-experts router sends
each token to its highest-scoring experts and splits the token between them", and lets them
check it. It opens with two active experts at temperature one, where Expert 1 receives 59.9%
of the token and Expert 4 receives 40.1%. Set **Active experts** to 1, and the top expert
receives all of it. Set it back to 2 and raise **Temperature** to its maximum of 2: the split
moves to 55.0% and 45.0%, closer together, but the order of the experts never changes.

<HtmlEmbed
  id="guide-routing"
  src="d3-routing.html"
  title="Routing example"
  desc="Illustrative scores [2.2, 1.3, 0.6, 1.8], not measurements from a trained model."
/>

The figure is one file, `app/src/content/embeds/d3-routing.html`, and that is the second rule:
**each figure has one source**. A figure is an HTML fragment with its own styles and script,
and the `HtmlEmbed` component places it in a chapter, gives it a title and caption, and starts
its script. The same file can appear in several chapters, or on a page of its own, without
being copied.

Inside that file, the calculation is a function apart from the drawing code, and the figure
records the function's exact output on each value label, next to the rounded percentage. This
is what makes the figure testable rather than merely interactive. The browser tests set every
combination of the two controls, read the exact weights, and confirm that they sum to one and
that temperature never reorders the experts, however the layout changes.

A figure also has a **publication state**: the state it opens in, which a reset restores. The
routing figure's publication state is two experts at temperature one. The state matters
beyond the website, because the PDF exporter replaces every figure with a screenshot of how it
opens. Choose that state, and its caption, so that the figure makes its point without anyone
touching it.

There are three ways to get a figure, in increasing order of effort: use one of the supplied
figures as it is, configure one with your own data, or adapt a copy of one for a new
interaction. Before starting on the third, check that the reader really has something to vary.

<Note title="When a static image is enough" variant="info">
  If readers would never change a parameter, an interactive figure adds code without adding
  understanding. A captioned `Image` is clearer, loads faster and prints exactly as it appears.
</Note>

<Accordion title="Build your own figure from an example">

Start from the supplied figure closest to what you need, in `app/src/content/embeds/`:
`d3-equation-editor.html` for expressions, `d3-routing.html` for a staged explanation,
`smol-playbook/generic-d3-line-chart.html` for curves, or `sankey.html` for flows. The
demonstration article has more, including a parameter calculator, a drawable neural network,
heatmaps, typography and arXiv clusters. Open `/dataviz/` in the preview to browse the figures
the current article uses.

Copy the example to a file with a descriptive name. Rename the root CSS class and the selectors
in your copy, so the two figures cannot affect each other on the same page, and keep the
attribution of any code you reuse. The full conventions are in the upstream embed skill,
`.ai/skills/create-html-embed/SKILL.md`, and its `directives.md`.

An embed has three parts: one root element, CSS scoped to that element's class, and a script
wrapped in an immediately invoked function. SVG, Canvas and D3 all work inside it, and React is
not needed. A few rules keep the figure reliable:

- Keep calculations in functions separate from the rendering code, so tests can check them.
- Keep state inside each instance, and guard against mounting twice, because a page can show
  the same figure more than once.
- Take colors from the template's CSS variables and `window.ColorPalettes`, and recompute
  colors calculated in JavaScript when the theme changes.
- Use labelled HTML controls, so the figure works with a keyboard.
- Size the figure from its container with a `ResizeObserver`, so it fits on a phone.
- Open on a meaningful publication state, and add a reset when readers can get lost.

</Accordion>

<Accordion title="Bring your own data">

Store CSV or JSON files in `app/src/content/assets/data/`. The site serves them at
`/data/FILENAME`, so open that address in the preview to confirm that a file is available.
Record the source, license, units and any transformations next to the data.

As an example, create `app/src/content/assets/data/example-loss.csv`:

```csv
run_name,tokens,loss
Illustrative A,0,3.0
Illustrative A,100,2.5
Illustrative A,200,2.1
Illustrative B,0,3.1
Illustrative B,100,2.7
Illustrative B,200,2.4
```

The supplied line chart reads it through its `config` prop:

```mdx
import HtmlEmbed from "../../components/HtmlEmbed.astro";

<HtmlEmbed
  src="smol-playbook/generic-d3-line-chart.html"
  title="Illustrative loss curves"
  desc="Invented values for demonstrating the chart."
  config={{
    dataUrl: "/data/example-loss.csv",
    xDomain: [0, 200],
    yDomain: [2, 3.2],
    smoothingWindow: 1,
  }}
/>
```

`HtmlEmbed` passes `data` and `config` to the figure without interpreting them, so the
figure's script decides what they mean. This chart reads `config.dataUrl`, while other figures
read a `data-datafiles` attribute on their wrapper. Read the loader in the script before
changing the shape of a dataset. In your own figures, validate numeric values and show a
readable message when loading fails.

Everything in the data folder is deployed, even when no chapter uses it, so keep private data
and credentials out of it. For a large dataset, sample or aggregate it and document the method,
rather than making every reader download detail the figure does not show.

</Accordion>

## Reuse a figure on another site

A figure in your article may also belong on your personal site or in a course page. The
second rule answers how: the figure keeps one owner. Its HTML source, data and tests stay in
this project, which publishes the figure on a standalone page, and the other site embeds that
page. An improvement then reaches both places with a single deployment, and there is no copy
to fall out of date.

[Open the same routing figure on its own](/figures/routing/). It has the same model and
controls as the one above, because both pages render the same file.

<Accordion title="Publish a figure for another website">

Add an entry for the figure to `app/src/content/figures.json`, next to the existing ones:

```json
{
  "my-figure": {
    "src": "d3-routing.html",
    "title": "A token chooses its experts",
    "description": "Illustrative scores and normalized routing weights.",
    "lang": "en"
  }
}
```

Replacing the whole file instead removes the other figures' pages. Build the site, and the page
appears at `/figures/my-figure/`. The optional `"frameless": true` lets a figure supply its own
heading and card. The registry accepts only these presentation fields, not `data` or `config`,
so a standalone figure must work with the defaults in its own source. Register a figure only
when another site will show it; a figure used only in the article needs no entry.

Once the site is deployed, another website can show the figure with an iframe:

```html
<iframe
  src="https://YOUR-ARTICLE-HOST/figures/my-figure/"
  title="A token chooses its experts"
  loading="lazy"
  style="width: 100%; height: 680px; border: 0"
></iframe>
```

Replace `YOUR-ARTICLE-HOST` with the origin of your deployment, and test the height at desktop
and phone widths, because the iframe keeps the height you give it. The figure follows its own
theme rather than the host page's, and the server hosting your article must allow framing.
When a paper needs a figure that never changes, link to a versioned deployment that you keep
online.

</Accordion>

Every figure so far has run in your preview, on your machine, with the controls in your hands.
A reader gets something else: a deployed website, or a PDF with no controls at all. How do you
check what they will receive before you send it?
