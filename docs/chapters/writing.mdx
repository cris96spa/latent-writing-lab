## Write the explanation

Your chapter is written in <Glossary term="MDX" definition="Markdown that can import and render components." />:
paragraphs, headings, lists and links are plain Markdown, and anything Markdown cannot express,
such as a callout, a captioned image or a figure, is a component you import from the template
and place like an HTML tag. The engine does the rest. It numbers the figures, builds the table of
contents from your headings and collects the references at the end.

Three additions answer the reader's questions from the end of the last chapter: a source for the
claim, a warning about which numbers are real, and the reasoning behind what the figure shows.
The first two take one line and one component:

```mdx
import HtmlEmbed from "../../components/HtmlEmbed.astro";
import Note from "../../components/Note.astro";

## The router's rule

A mixture-of-experts layer sends each token to only a few
of its experts [@hf-moe]. A router scores every expert, ...

<Note title="The scores are illustrative" variant="info">
  The scores show the mechanism; no trained model made them.
</Note>
```

`[@hf-moe]` cites a record in `app/src/content/bibliography.bib`, which the starter includes;
the engine turns it into "(Hugging Face, n.d.)" with a link to a reference list at the end of
the page. For a source of your own, add its BibTeX record to that file, copying the DOI and
other metadata from the source itself rather than reconstructing them, and cite it by its key.
Any chapter can cite any record. The `Note` sits above the figure, where a reader looks before
trusting the numbers, and its title states the point, so a reader who skims still gets it.

The same care applies to everything a reader will take as fact. Every author, affiliation,
source and measurement must be real and checked, and when a value is invented to illustrate a
mechanism, the text or the caption says so, as your article does twice.

The third addition, the reasoning, is ordinary prose: start each section at `##`, because the
article title is the page's only top-level heading, and write the explanation the figure
supports. A longer article splits into several chapters, each imported by the entry file in
reading order, and all of them cite from the same bibliography. That lets you draft a
section in its own file, and the first rule says what happens to it.

<Note title="Everything you import is published" variant="danger">
  The engine has no draft flag. A half-written chapter that the
  entry file imports is built and deployed with the rest, so keep it
  out of the imports until it is ready to be read, and keep a
  visible draft label in the article while it is under review.
</Note>

A chapter can also run code. An import or an expression in MDX executes when the site builds,
so review chapter changes as carefully as you would review code. Write the prose and figure
labels in your article's language; the template's own interface, such as its buttons and table
of contents, stays in English unless you change the engine.

Which component to reach for depends on what the content does for the argument, not on how it
should look.

<Accordion title="Choose a component for what you need to say">

| When you need                                         | Use                                           |
| ----------------------------------------------------- | --------------------------------------------- |
| A distinction or assumption readers must notice       | `Note`                                        |
| A short clarification alongside the argument          | `Sidenote`                                    |
| A definition without leaving the paragraph            | `Glossary`                                    |
| An optional derivation, setup command or code example | `Accordion`, like this one                    |
| An attributed passage                                 | `Quote`                                       |
| An image with caption, zoom and alt text              | `Image`                                       |
| A comparison of two or more visuals                   | `Stack`                                       |
| More room for a diagram                               | `Wide` or `FullWidth`; check mobile and print |
| A caption and anchor around another element           | `Reference`                                   |
| Something readers can vary                            | `HtmlEmbed`                                   |
| A flow or dependency diagram                          | `HtmlEmbed` with an SVG diagram               |
| Audio or an externally hosted app                     | Native `<audio>` or a titled `<iframe>`       |

A chapter directly inside `chapters/` imports a component from `../../components/Name.astro`,
and a chapter one folder deeper needs one more `../`. The demonstration article shows every
component in use; its source is in `app/src/content/chapters/demo/components.mdx` and
`markdown.mdx`.

</Accordion>

When the reader does not need to vary anything, an image is the simplest evidence a chapter can
carry. The `Image` component optimizes the file, adds the caption and lets readers select the
image to zoom in:

<Image
  src={vocabulary}
  alt="Financial Times visual vocabulary: chart families for relationships including change, distribution, correlation and flow"
  caption="Visual Vocabulary, Financial Times. Image included in the upstream template."
/>

<Accordion title="Add images, math, links, footnotes and audio">

Put images in `app/src/content/assets/image/` and import them, so the build can optimize them.
Give each one alt text that conveys its information, for readers who cannot see it, and a
caption that states its role and source:

```mdx
import Image from "../../components/Image.astro";
import picture from "../assets/image/placeholder.png";

<Image
  src={picture}
  alt="Describe the information shown"
  caption="Explain and credit the image."
/>
```

Write inline math between single dollar signs, `$...$`, and display math between double ones,
`$$...$$`. KaTeX renders it and supports most but not all LaTeX commands, so check anything
beyond the basics in the preview. Code fences display code; they never run it.

To link to a figure, give it a unique `id` and link to `#your-id`, as in
`[the example](#your-id)`. Markdown footnotes hold supporting context, and the `article` layout
collects them with the references.

For audio, import a file from `../assets/audio/`, place it with
`<audio controls src={audioUrl} />` and provide a transcript. For an iframe, give it a
descriptive title and a size you have tested at phone width; the remote host must allow
embedding and stay online for your readers.

</Accordion>

<Accordion title="Convert a LaTeX or Notion draft">

The template includes importers that convert an existing draft to MDX. Both can overwrite
`article.mdx` and copy assets into the project, so commit your work first and run them on a
separate branch or in a disposable copy.

For LaTeX, install Pandoc and place `main.tex`, `main.bib` and the related section files in
`app/scripts/latex-importer/input/`, then run:

```sh
npm run latex:convert
```

For other paths, see `npm run latex:convert -- --help`. Review the equation macros, references,
images and component imports in the result.

For Notion, give an integration access to the page, set `NOTION_TOKEN` and `NOTION_PAGE_ID` in
your shell environment, and run `npm run notion:import`. Never commit the token. The importer
empties its output directory and can change the article and the bibliography, so inspect
`git diff` and build before accepting the result.

An import is a one-way conversion. Once you accept it, edit the MDX; a later import replaces
your edits instead of merging with them.

</Accordion>

Your article now explains its claim and says where it comes from. The figure, though, is still
something you borrowed: you placed it with one tag and never looked inside. To build figures of
your own, you need to know what is in that file.
