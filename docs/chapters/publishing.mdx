## Check, build and publish

The preview you have been writing in is not what readers get, and that is the third rule:
**readers get the build, not your preview**. `npm run dev` compiles each page on request from
your live source. `npm run build` writes a static site to `app/dist`, and that site, or a PDF
made from it, is what reaches readers. So publishing is three steps in a fixed order: check the
build, export what you need from it, and put it where readers can reach it.

### Check the build

Three commands each answer a different question:

- `npm run check` confirms that the engine's files match their pinned versions and that your
  project is formatted, then builds the article.
- `make doc-check` checks the documentation's links and builds this guide, which lives in your
  project too and has its own tests.
- `npm run test:e2e` opens both builds in Chromium and operates their figures the way a reader
  would.

Install the browser once with `npx playwright install chromium`, then run them in order. The
tests serve the builds the first two commands made, so they always come last:

```sh
npm run format
npm run check
make doc-check
npm run test:e2e
```

A passing `npm run check` ends with the build, and the page count includes the three
registered figure pages:

```text
Verified 98 upstream files and 3 standalone figures. Astro validates and compiles MDX during build.
...
[build] 5 page(s) built in 4.44s
[build] Complete!
```

On your article, one browser test fails, and its message says why. The first test in
`e2e/article.spec.ts` was written for the demonstration and still expects its title:

```text
Error: expect(locator).toContainText(expected) failed

Locator: getByRole('heading', { level: 1 })
Expected substring: "Bringing paper to life:"
Received string:    "How a router splits a token"
```

Replace that test, `complete upstream demo renders its chapters and local assets`, with one that
checks your article. It operates the figure as a reader would and checks the claim your
article makes about a single active expert:

```ts
test("my article explains routing", async ({ page }) => {
  await page.goto("/");
  await expect(page.getByRole("heading", { level: 1 })).toHaveText(
    "How a router splits a token",
  );
  await expect(page.locator(".katex").first()).toBeVisible();
  await expect(page.locator(".html-embed__error")).toHaveCount(0);
  await page
    .getByRole("slider", { name: "Active experts (k)" })
    .fill("1");
  await expect(page.locator(".routing-value").first()).toHaveText(
    "100.0%",
  );
});
```

Keep the file's imports, its D3 setup and the standalone figure tests, then run
`npm run test:e2e` again; all six article tests pass. For a figure of your own, test the
properties its model must keep, as the routing tests do: weights that sum to one, values that
stay in range, or a curve that changes as expected.

None of these checks can tell whether a sentence is true or a figure makes its point. That
review stays with you and your reviewers, in a pull request, where GitHub CI repeats the same
checks on Node 22 and 24 and keeps the builds as downloadable artifacts for 14 days.

### Export a PDF

A PDF is the build with the controls removed. The exporter opens the built article in Chromium
and replaces every figure with a screenshot of its publication state, which is why the last
chapter asked you to choose that state with care. Build first, and stop any preview on port
8080, because the exporter starts its own:

```sh
npm run build
npm run export:pdf -- --filename=article --theme=light --wait=full
```

For your article, the output ends like this; the two screenshots are the banner and the routing
figure:

```text
📸 Screenshotting embeds…
   2 embed(s) replaced with screenshots
...
✅ PDF generated: …/app/dist/article.pdf
✅ PDF copied to: …/app/public/article.pdf
```

Open `app/dist/article.pdf` and read it: the equation, the caption, the reference and the page
breaks. Wide charts can be clipped, and iframes that show external applications rarely print
usefully. The exporter also writes the social preview thumbnails.

<Accordion title="Export LaTeX or images, and ship the PDF">

For LaTeX, install Pandoc and run `npm run export:latex -- --filename=article`, which writes
`app/dist/article.tex`; its `--pdf` option also needs `pdflatex`. For PNG images of the figures,
run `npm run preview`, then `npm run export:images` in a second terminal. The images are written
to `app/screenshots/`.

Git ignores generated files, so a clean build or a container image does not contain a PDF you
exported locally: make the reviewed export part of what you deploy. The download button of the
`article` layout links to a filename derived from the title, so use the exporter's default name
or link to a custom name yourself, then open the public download address to confirm it works.
The `paper` layout has no download button.

</Accordion>

### Publish

The last step is one you take on purpose. Nothing in the project publishes your article on its
own, so you choose a host and put the reviewed build there yourself.

<Note title="Deployment is always a step you take" variant="danger">
  CI builds and tests every push but never publishes your article.
  Pushing to a Hugging Face Space, by contrast, publishes the pushed
  revision as soon as the Space has built it, so push only commits
  you have reviewed.
</Note>

On a static host, deploy the complete contents of `app/dist/` at the root of an origin, keeping
`_astro`, `data`, `scripts` and the figure pages together. The site loads its files through
root-relative addresses, so it needs an origin of its own; serving it under a subpath means
adapting the engine's base path. The supplied Dockerfile serves the same build with nginx:

```sh
docker build -t my-article .
docker run --rm -p 8080:8080 my-article
```

<Accordion title="Host the article on Hugging Face">

Create a **Docker Space**. A Space reads its settings from a YAML block at the very top of the
root `README.md`, so add one before the README's first heading. The `research-article-template`
tag lists the article in the Hugging Face gallery of template articles:

```yaml
---
title: YOUR ARTICLE TITLE
sdk: docker
app_port: 8080
tags:
  - research-article-template
---
```

Then push your reviewed commits to the Space with your usual Git authentication, replacing
`YOUR-OWNER` and `YOUR-SPACE`:

```sh
git remote add hf https://huggingface.co/spaces/YOUR-OWNER/YOUR-SPACE
git push hf HEAD:main
```

The push starts a build on Hugging Face. Follow its logs, then open the public page, its data
and its download links. Keep tokens out of remote addresses and source files. The image does not
generate a PDF during its build. For canonical addresses and a sitemap on any other host, set
your site's origin in the Astro configuration.

</Accordion>

Once the article is live, open it as a reader would: on a phone, in both themes, with the
downloads. When something looks wrong, the stage where it shows up narrows down the cause.

<Accordion title="When something does not look right">

| Where           | What you see                     | What to try                                                                     |
| --------------- | -------------------------------- | ------------------------------------------------------------------------------- |
| Preview         | Your chapter is missing          | Import it and place its tag in `article.mdx`.                                   |
| Preview         | `Embed not found`                | Match `src` to a file under `embeds/`, including its case.                      |
| Preview         | An empty chart                   | Check the browser console, CDN access and the `/data/...` response.             |
| Preview         | A data file returns 404          | Check the filename and the `app/public/data` symbolic link.                     |
| Preview         | A stale import error             | Restart the development server after changing dependencies.                     |
| Build           | MDX will not compile             | Check relative imports, unclosed tags, braces and code fences.                  |
| Build           | A citation does not resolve      | Match its key to a valid BibTeX record.                                         |
| Check           | A provenance check fails         | Review the named template file; never re-record hashes to silence it.           |
| Production view | The page shows old text          | Rebuild; `npm run preview` serves the last build.                               |
| Deployed site   | The PDF download is missing      | Include the matching PDF in the deployed site.                                  |
| Deployed site   | A figure works locally, not live | Check the browser console: figures load D3 from a CDN, which must be reachable. |

Some limits come from the template itself. Its demonstration references a citations chart,
`d3-hf-citations.html`, that upstream never supplied, and the live upstream page shows the same
gap. The demonstration also loads libraries from CDNs and embeds external pages, so not every
example works offline.

</Accordion>

## The whole path in one list

Each chapter added one piece to the same article. Put together, they make the recipe for every
article you publish from this starter:

1. Create a repository with **Use this template**, clone it, and run `npm ci` and `npm run dev`.
2. Write a chapter in `app/src/content/chapters/`, and make `article.mdx` import only your
   chapters. What you import is what you publish.
3. Cite your sources from `bibliography.bib`, mark illustrative values as such, and replace
   the demonstration's metadata with your own.
4. For each mechanism a reader should test, place a figure with `HtmlEmbed`, keep its model
   apart from its drawing, choose its publication state, and test the properties the model
   must keep. Each figure has one source.
5. Register a figure in `figures.json` only when another site will show it, and remove the
   starter's entries you do not want published.
6. Run `npm run check`, `make doc-check` and `npm run test:e2e`, then review the prose, sources
   and figures in a pull request.
7. Build, export the PDF and read it. Readers get the build, not your preview.
8. Deploy `app/dist` or the container, then open the public page and its downloads.

How the kit fits together, every command and the way the engine is updated are in the
repository's
[How it works](https://github.com/cris96spa/latent-writing-lab/blob/HEAD/docs/how-it-works.md)
and [Reference](https://github.com/cris96spa/latent-writing-lab/blob/HEAD/docs/reference.md)
pages.
